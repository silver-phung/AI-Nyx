## 1. Context and Problem Statement

The AI-Nyx project (fork of StablyAI Orca) is a next-generation parallel agentic development environment. The Owner wishes to introduce **Pantheon Office 3D**—an interactive virtual office interface where AI agents appear as virtual employees working at desks, collaborating, and executing tasks.

The Owner requires **100% preservation of all existing Orca features**:
1. **Classic View** (terminal panes, tab groups, splits, editor, browser) must remain fully functional.
2. **Office 3D is an additional interactive view**, **NOT** a new Agent runtime or second orchestration system.
3. Every 3D employee must map directly to an existing Orca agent pane.
4. Workspace creation, session history, Git, Tasks, Automations, Orchestration, permissions, and all other Orca features must remain accessible.
5. In-office real chat and terminal interaction are **RELEASE-BLOCKING requirements for Milestone M7/M8**.
6. Zero duplicate agents, zero redundant LLM queries, and no separate Pantheon Python engine, Tauri shell, or sidecar daemons.

This Architecture Decision Record (ADR) establishes the findings of **Milestone M0 (Baseline Verification & Architecture Preparation)** to ensure complete safety and architectural alignment before any implementation begins.

## 3. Owner Product Decisions (D1–D6) — PROPOSED

The six core product decisions defined during the initial architecture audit are recorded below. All remain **PROPOSED** pending explicit Owner sign-off:

### D1: Employee Identity — PROPOSED
- **Concept**: Exactly one real Orca agent pane per 3D employee.
- **Grouping**: Workspaces group desks; agents within a workspace occupy neighboring desks in the 3D office layout.
- **Invariant**: No phantom or decorative employees without an underlying Orca agent or terminal session.

### D2: Employee Interaction — PROPOSED
- **Initial Phase (M1–M6)**: Clicking a 3D employee focuses the exact workspace and invokes `revealTerminalPane({ worktreeId, tabId, leafId })` to jump to the Classic Terminal pane.
- **Release Requirement (M7/M8)**: **Real interactive in-office Chat and Terminal are RELEASE-BLOCKING**. Users must be able to inspect output and send input directly within the 3D office surface before production release.

### D3: Sidebar & Project Navigation — PROPOSED
- **Behavior**: The Left Sidebar (Projects, Workspaces, Git status) remains accessible while in Office 3D.
- **Target Integration**: In the final product, a dockable chat/inspector companion panel can open alongside the 3D canvas without occluding workspace navigation.

### D4: Visual Assets and Feature Naming — PROPOSED
- **Feature Name**: Formally named **Office 3D** in UI labels and settings.
- **Assets**: Curated, properly licensed Pantheon 3D resources (`.glb`, textures). No unvetted or external assets will be imported without license verification.

### D5: Platform Scope — PROPOSED
- **Primary Target**: Windows 11 x64 first.
- **Constraint**: Must not break existing macOS, Linux, or WSL native build pipelines, packaging scripts, or CI gates.

### D6: Meeting Rooms — PROPOSED
- **Layout**: Meeting room geometry and collaborative areas will be modeled in the 3D environment.
- **Orchestration**: Live multi-agent conference/orchestration logic will be deferred to its dedicated milestone, avoiding early complexity.

## 4. Architecture Decisions (AD-1 through AD-6) — PROPOSED

The following engineering decisions are **PROPOSED** to guide technical implementation:

### AD-1: Pure Native Architecture — PROPOSED
Office 3D is strictly an additional top-level view within the existing Electron renderer. It will **not** incorporate Pantheon's Python backend, Tauri shell, or any secondary IPC daemon. Zero duplicate LLM calls; pure React and WebGL/Three.js inside Orca's Electron renderer.

### AD-2: Unified Agent State via Dashboard Snapshot — PROPOSED
3D employee states map 1:1 to Orca agent panes by reading real-time fleet state from `useLiveDashboardSnapshot()`, avoiding custom polling or redundant state machines.

### AD-3: Non-Destructive View Retention — PROPOSED
Classic View (`<Terminal />`) remains mounted in DOM (`hidden`/`inert`) during Office 3D viewing. Live local PTYs and background agent execution continue without interruption.

### AD-4: Click-to-Focus via revealTerminalPane — PROPOSED
Interacting with any 3D employee routes through `revealTerminalPane({ worktreeId, tabId, leafId })` to jump into the full Classic Terminal view.

### AD-5: Phased Zero-Asset M1 Scope — PROPOSED
Milestone M1 is strictly a DOM-only placeholder with feature flag default OFF. Zero Three.js/Canvas/Pantheon assets in M1.

### AD-6: Git Documentation Tracking Strategy — PROPOSED
Keep `docs/office3d` local in the worktree until the Owner approves adding `.gitignore` allowlist exceptions (`!docs/office3d/` and `!docs/office3d/**`).

## 6. Deep-Dive: Terminal Parking, Session Lifetimes, and Runtime Differences

### 6.1 Renderer Parking vs. PTY Lifecycle
- **What is Parked**: Cold parking unmounts `<TerminalOverlaySlot>`, XTerm DOM elements, canvas nodes, WebGL instances, and frontend byte parsers.
- **Local PTY Lifetimes**: For local processes, the Node-PTY process, execution host daemon, background shell, and CLI runners (e.g., Claude Code CLI) remain running. Background output continues buffering in the daemon's circular snapshot buffer.
- **Sidecar Watchers**: When parked, Orca attaches a lightweight `startParkedPtyWatcher` in the renderer to listen for exit codes, bells, and runtime titles without rendering pixels.

### 6.2 Host-Specific Differences & Exceptions
1. **Local Worktrees**:
   - PTY ID format: `${worktreeId}${PTY_SESSION_ID_SEPARATOR}${sessionId}`.
   - Restored from daemon snapshot buffer (`isSnapshotBackedTerminalPty`).
   - *Exception*: Fail-open PTY IDs (spawned without an authoritative daemon session model) are **exempt from parking** because remounting would respawn the shell instead of restoring state.
   - *Exception*: Foreign-worktree PTYs (where PTY ID prefix does not match the active worktree ID) refuse parking.
2. **SSH Worktrees**:
   - PTY execution occurs on the remote SSH server.
   - Controlled by `settings.terminalSshViewParking !== false`.
   - **Tunnel Dependency**: If the SSH connection drops while parked, the process on the remote machine may survive (if managed by tmux/daemon) or terminate; the renderer watcher captures negative exit codes via `markUnverifiedPtyLoss` to preserve the tab UI across reconnects.
   - **Claim Correction**: Absolute claims that SSH connections always remain active during parking are **unsupported**. Network drops, server disconnects, or SSH timeouts can sever the tunnel while parked.
3. **WSL & Remote Paired Runtimes**:
   - WSL and remote runtime environments (`isRemoteRuntimePtyId`) require the remote host to advertise the `terminal.paired-parking.v1` capability (`TERMINAL_PAIRED_PARKING_RUNTIME_CAPABILITY`).
   - **Capability-Unknown Exception**: If the capability is unverified, absent, or fails handshaking, **parking is vetoed** (`canWatcherCoverParkedTerminalTab` returns `false`), keeping the pane warm in DOM.
4. **Retention and Force-Parking Limits**:
   - Cold park delay: `TERMINAL_WORKTREE_COLD_PARK_DELAY_MS = 30_000` (30s).
   - Hot retention preserves the most recently visited worktrees (`TERMINAL_WORKTREE_HOT_RETAIN_LIMIT = 4`) and tabs (`TERMINAL_TAB_HOT_RETAIN_LIMIT = 6`).
   - Force-parking (`isForceParked`): When the retention budget is exhausted under high memory pressure, even warm worktrees may be force-parked, preserving only active tabs.
5. **Snapshot & Scrollback Limits**:
   - If a background process outputs megabytes of logs while parked, the circular daemon buffer caps history (`DASHBOARD_MAX_LABEL_LENGTH` / circular PTY buffer). Truncated scrollback is a known constraint upon remount.
6. **Native Chat & Structured Claude Session Risks**:
   - Structured native chat tabs use `StructuredAgentSessionPaneOverlayLayer`. Underlying execution tools use PTYs.
   - If an underlying PTY exits, `shouldDeferParkedPtyExitTabClose` defers tab destruction until the user reveals the pane, avoiding accidental closure of live sibling leaves.

### 6.3 Unverified Behaviors Requiring Runtime Testing
The following behaviors cannot be validated by static inspection and are marked **UNVERIFIED until tested**:
- **System Sleep / Hibernate**: Behavior of background PTYs and SSH tunnels during OS sleep/wake cycles while in Office 3D.
- **App Restart Restoration**: Whether an app relaunch directly into `activeView: 'office3d'` cleanly reconstitutes parked session models without spurious spawns.

## 7. CSP & Production 3D Asset Loading Correction

- In development mode, Vite serves assets via `http://localhost:<port>/` with a relaxed CSP.
- In production packaged builds (`dist/win-unpacked/`):
  - Assets are loaded from `file://` or custom protocol schemes (`app.asar`).
  - Three.js `GLTFLoader` uses `fetch()` or `XMLHttpRequest` internally to read binary `.glb` files and textures.
  - While `src/renderer/index.html` has no explicit `script-src 'none'`, **production loading of local binary 3D assets (`.glb`, `.gltf`, textures) cannot be proven by source inspection alone.**
  - **Verdict**: Production GLB and texture loading is **UNVERIFIED** until packaged-build smoke tests are conducted in a later milestone (M3/M4). M1 avoids this risk entirely by using a zero-asset DOM placeholder.

## 9. Dashboard Snapshot: Frequency & Performance Architecture

Orca provides real-time fleet state via `useLiveDashboardSnapshot()`:

- **Update Frequency**:
  - Driven by Zustand state subscriptions: `agentStatusByPaneKey`, `runtimePaneTitlesByTabId`, `worktreesByRepo`, etc.
  - **Does NOT fire per-token or per-stdout-byte**. Byte streaming is decoupled from the UI store.
  - Fires only when agent lifecycle states change (`working` -> `waiting` -> `done`), tool invocations begin/end, or tab titles change.
- **3D Render Loop Architecture (M2+)**:
  - *Risk*: Subscribing directly to `useLiveDashboardSnapshot()` inside a 60 FPS React render tree would cause catastrophic React re-render cascades.
  - *Required Architecture*: Decouple store updates from the 3D frame loop. Store updates write to a mutable ref (`officeFleetRef.current = snapshot`). The 3D render loop (`requestAnimationFrame` / `useFrame`) reads from `officeFleetRef` without triggering React reconciliation.
